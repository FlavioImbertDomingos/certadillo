# Security model

## Assets

| Asset | Why it matters |
| --- | --- |
| Root and issuing CA private keys | Anyone holding them can mint trusted identities for the whole estate |
| SSH CA key | Same, for server access |
| API keys, EAB credentials, SCEP challenges and CMP secrets | Let a caller obtain certificates inside an app's scope |
| Manufacturer CAs registered for EST | Let every device from that factory enroll into an app |
| Audit trail | Evidence for auditors and incident response |
| Inventory | Tells an attacker where the weak endpoints are |

## Threats and controls

[THREAT_MODEL.md](THREAT_MODEL.md) ranks the assets and walks each attack path end to end; this table is the per-threat summary.

| Threat | Control in this codebase |
| --- | --- |
| CA key theft | PKCS#11 signer: keys generated on the HSM as `CKA_SENSITIVE=true`, `CKA_EXTRACTABLE=false` (asserted in tests). Vault Transit signer: keys created non-exportable with plaintext backup off, version pinned, every signature verified against the CA certificate's key; the shipped application policy cannot sign with the root or change any key. Software keys are PKCS#8 encrypted and meant for labs only. |
| Mis-issuance to the wrong name | Every DNS SAN, SPIFFE ID, email address and host-name CN is checked against the app's approved scope. URI and email SANs are only accepted by the profiles meant for them. ACME orders outside the scope are refused before any challenge. |
| A single insider issuing code-signing certs or new CAs | Maker-checker: only the approver role decides, the requester cannot approve, and an approver credential minted by the requester cannot approve that requester's requests. Approvals are audited. Production onboarding also needs a second person. |
| Stolen app credential | Scope-limited to one app's names and profile, and no read access to other apps or reports; short certificate lifetimes; `POST /api/v1/principals/{name}/deactivate`; renewal forces a new key pair. |
| Replay of ACME requests | Single-use nonces, committed as spent before the request is processed; JWS `url` must match the request path. |
| Weak keys submitted by clients | Minimum RSA size, allowed curves, CSR signature check (proof of possession). |
| Tampering with the audit log | SHA-256 hash chain, verify endpoint, `certadillo_audit_chain_valid` metric and a critical alert. Appends are serialized with a PostgreSQL advisory lock, and `prev_hash` is unique so a race fails instead of forking the chain. `CERTADILLO_AUDIT_SHIP` sends every event within seconds to a SIEM (syslog over TLS, Splunk HEC, HTTPS) and/or S3 with Object Lock, each record signed with Ed25519 so receivers can verify with the public key but not forge; the shipper stops and alerts if shipped history is rewritten. |
| Silent expiry | Lifetime-aware expiry alerts, per-team routing, Prometheus rules as an independent path. |
| Revocation not visible to relying parties | OCSP answers from live state; a new CRL is signed on every revocation and on a timer; CRLStale alert. |
| Rogue certificates on the network | Discovery scans and connectors; unowned and weak certificates raise alerts. |
| A forged client-certificate header on EST | The header is believed only with the load balancer's shared secret (constant-time compare) or from a listed proxy address; otherwise it is ignored and logged. The certificate must then be current and issued here, or chain directly to a manufacturer CA registered for one app. |
| Trusting a manufacturer CA too widely | Anchors are per app, so bootstrapped devices only get names in that app's scope; adding one to a production app takes a second person. |
| A SCEP validation webhook that is down or wrong | Fail closed: no answer, an error or anything but `{"valid": true}` refuses the request, and the reason is audited. |
| CMP shared secrets | One-time, short-lived, bound to one app, and stored encrypted (Fernet, key derived from `CERTADILLO_KEY_PASSPHRASE`), because the MAC needs the plaintext. PBM iteration counts above 100,000 are refused so a request cannot burn CPU. |
| Keys generated by the server (EST serverkeygen) | Only for profiles that allow it, never stored, returned only inside TLS, audited with `"stored": false`. |
| Taking services down during a mass revocation | Renewal campaigns replace certificates first (ARI); revoking the ones without a successor needs a second person. |
| A Windows logon certificate minted for another account's SID | The SID is resolved from the directory by name, never read from the request, and the lookup fails closed (zero or many matches issues nothing). Disabled accounts are refused and sensitive accounts (adminCount=1) need a second approver. The UPN suffix must be in the app's scope. |
| The AD CS template audit itself becoming an attack tool | It is read-only: it reads templates and CA config over an ordinary LDAP bind (or an offline export) and never enrolls, edits or exploits anything. It reports the same findings a defender would want, so templates can be fixed. |
| A compromised AD CS gateway worker | The gateway only carries out requests Certadillo already approved under policy and scope; it cannot decide policy. Its principal has its own `gateway` role, and every job is audited. It should run on a hardened, domain-joined host with least-privilege CA rights. |
| A stolen long-lived credential | With an external IdP configured, access uses short-lived OIDC/JWT tokens validated against the issuer's JWKS (signature, issuer, audience, expiry, allowed algorithms, never `none`), mapped to a role by claim. No shared secret is stored, and the IdP's own session revocation applies. Every validation failure is fail-closed. See [Zero-trust access](guide/21-zero-trust-auth.md). |
| Someone with write access to the database (a stolen DB credential, SQL injection, a rogue DBA) | Principals, approvals and certificate status carry an HMAC seal keyed outside the database. A row changed in SQL fails its seal: the principal cannot log in, the approval cannot be decided, and OCSP and the CRL report the certificate as revoked. A restored old copy of a row is caught by cross-checking the audit trail. `IntegritySealBroken` fires either way. |
| Rewriting the audit trail | The audit table is append-only in the database (triggers; on PostgreSQL `certadillo db harden` leaves the application role with SELECT and INSERT only, so it cannot drop them). The chain head is anchored off the host daily; `certadillo audit verify --anchors` and `AuditAnchorMismatch` catch a history that was rewritten and re-hashed. |
| A stolen issuing CA key used for names outside the bank | `CERTADILLO_CA_PERMITTED_DNS` writes critical name constraints into new issuing CAs, so relying parties reject certificates for other names even if the key is stolen. |
| Script injected through data the console shows (a hostile certificate subject, team name or error message) | The console builds HTML only through an escaping tagged template, loads no inline script, and runs under a CSP with Trusted Types, so a raw `innerHTML` write throws. The knowledge base runs under the same kind of policy. API responses carry `default-src 'none'`. Browser responses also get `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, and HSTS behind TLS. |
| A compromised third-party GitHub Action | Actions are pinned to commit SHAs and kept current by Dependabot; the workflow token is read-only except where a job needs one extra scope; checkout does not persist credentials. |
| An admin or operator labelling an app "dev" to skip the second person | The label does not decide it. Onboarding skips approval only for a non-prod app whose whole scope is inside `CERTADILLO_DEV_DOMAINS`; unset, every onboarding needs an approver. Scopes broader than `*.two.labels` are refused, and an approval is re-checked when it is decided (the app still in the expected state, the requester still active). |
| A forged directory answer putting another account's SID in a logon certificate | LDAP is TLS-only (LDAPS, or StartTLS before the bind) with the domain controller's certificate validated against `CERTADILLO_ADCS_LDAP_CACERT` or the system store. Plain LDAP needs an explicit lab-only switch. |
| CA keys protected by a passphrase anyone can read | There is no built-in passphrase. Unset, a random one is generated into the data directory with mode 0600; known placeholders and short values are refused at startup. |
| A ceremony token creating its CA key as exportable | The generated ceremony policy allowlists the key-creation parameters (`exportable` and `allow_plaintext_backup` only as false). A denylist would not work: Vault compares values literally, so `"true"` as a string gets past a deny on `true`. Tested against Vault. |
| A certificate row flipped back to active in SQL being used to log in to EST | Certificate login uses the sealed status, the same check OCSP and the CRL use. |
| An admin loosening policy alone, or an app escaping its business line's rules | Policy folders hold bank-wide and per-line rules; a locked setting cannot be changed below its folder. Creating or changing a folder and moving an app are approval requests. Apps and folders are sealed, so a database write that moves an app or widens its scope stops its issuance. |
| An upstream CA (public ACME, DigiCert, AWS Private CA, EJBCA) issuing something other than what was approved | Policy runs before the request leaves Certadillo, and the returned certificate must carry the requested public key and no DNS name the policy did not approve; otherwise nothing is stored or returned. API keys, EAB and TSIG secrets are references; the ACME account key is stored encrypted with the key passphrase. |
| A leaked machine key (host agent, AD CS gateway) used to read the estate | `agent` and `gateway` are separate roles that can only post reports or work their job queue. A test sweeps every GET endpoint with both and fails if either can read inventory, approvals or configuration. |
| Private keys left readable on servers, and public certificates for the bank's names issued outside the platform | The host agent reports key file permissions (never the keys) and opens a critical `PrivateKeyExposed` finding; CT monitoring opens an `UnknownPublicCertificate` finding for every unexpired public certificate under the bank's zones that Certadillo did not issue. |
| Push provisioning credentials (SSH keys, F5 passwords, cluster tokens) leaking from Certadillo | Targets hold references (`env:`, `file:`, `vault:`), never values, and a config with secret-looking keys is refused. SSH host keys are pinned, paths are limited to the target's allowed directories, and the reload command is set by an admin. A target serves only its own team's apps. Targets and installations carry integrity seals, so a database write that repoints a target or adds a reload command stops the run before it connects. Centrally generated keys live only in the run's memory; a certificate whose push failed is revoked. |
| A build agent or a pipeline change used to sign malware with the bank's code-signing key | Code-signing keys are generated in the HSM or Vault and never exported. Pipelines send digests; a release key signs only after an approver who is not the requester agrees, and every signature is audited with the artifact name, version and digest. Only the owning app can ask a key for a signature. |
| Code running in the container (a dependency or parser bug) persisting or escalating | The image runs as uid 10001. The shipped compose files add a read-only root filesystem (state only in the data volume, `/tmp` a small tmpfs), drop every Linux capability, set `no-new-privileges` and cap the process count. Dependabot watches the Python, Docker and Actions dependencies. |

## Supply chain

| Control | Where |
| --- | --- |
| Base image pinned by digest | `Dockerfile`; Dependabot (docker) moves the pin |
| Every Python dependency pinned with its SHA-256 hashes | `requirements/image.txt`, installed with `pip install --require-hashes`; the application wheel goes in with `--no-deps` and `pip check` confirms nothing is missing |
| Known-vulnerability check on the locked dependencies | `pip-audit` in CI and before every release |
| Image vulnerability scan and SBOM | Trivy (critical and high) and a CycloneDX SBOM in CI |
| Signed release images | `.github/workflows/release.yml`: on a version tag the image is pushed to GHCR, signed with Sigstore keyless signing (bound to the workflow's GitHub identity, logged in Rekor), and the SBOM attached as a signed attestation |
| Actions pinned to commit SHAs | every workflow; Dependabot keeps the pins current |
| Fuzzing of the parsers that take bytes from unauthenticated clients | `tests/test_fuzz_parsers.py` (Hypothesis): SCEP, CMP, EST, OCSP, ACME JWS, CSR and PEM input, and the AD CS security descriptor parser. Every corrupted message must get a protocol error, never a server error. The first runs found four crashes (an unreadable CSR key, an unknown OCSP hash algorithm, a truncated security descriptor, an imported certificate with an unknown key algorithm), all fixed |

Regenerate the lock after changing dependencies in `pyproject.toml`:

```bash
pip install pip-tools
pip-compile --generate-hashes --allow-unsafe --strip-extras \
  --extra postgres --extra hsm --extra provisioning --output-file requirements/image.txt pyproject.toml
pip-audit --require-hashes --disable-pip -r requirements/image.txt
```

Verify a release image before deploying it:

```bash
cosign verify ghcr.io/flavioimbertdomingos/certadillo:v0.2.0 \
  --certificate-identity-regexp '^https://github.com/FlavioImbertDomingos/certadillo/\.github/workflows/release\.yml@refs/tags/v' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
cosign verify-attestation --type cyclonedx ghcr.io/flavioimbertdomingos/certadillo:v0.2.0 \
  --certificate-identity-regexp '...same as above...' --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

A longer fuzzing run: `CERTADILLO_FUZZ_EXAMPLES=5000 pytest tests/test_fuzz_parsers.py`.

## Known gaps in this MVP

These are listed so nobody deploys the MVP to production thinking they are handled.

1. API-key authentication is still the default and is single-factor. Configure the OIDC/JWT support (Entra ID, Vault, or any OIDC issuer) so access uses short-lived tokens from your IdP instead; see [Zero-trust access](guide/21-zero-trust-auth.md). Keep one break-glass admin key for when the IdP is unreachable. A browser SSO flow for the console is still to come.
2. EST client-certificate authentication depends on the load balancer: its shared secret must stay secret, and it must overwrite the client-certificate header on every request. mTLS between the load balancer and Certadillo would remove the shared secret; it is not built in.
3. ACME `http-01` validation follows redirects and uses the platform's network position (it runs off the event loop, so a slow target only delays its own order). dns-01 trusts whatever the configured resolvers answer, from one vantage point. Restrict egress, point the DNS views at resolvers you control, or use `ra-scope` mode for purely internal names.
4. Secret columns (EAB HMAC keys, CMP secrets, team webhooks) are encrypted at rest, by default with a key derived from `CERTADILLO_KEY_PASSPHRASE`. Someone who has both the database and the passphrase can read them; use `CERTADILLO_FIELD_CIPHER=vault` to keep that key in Vault Transit.
5. No rate limiting. Put the API behind a gateway with per-principal limits.
6. The SSH CA key is a software key. Move it to the HSM (OpenSSH supports PKCS#11 CA keys through `ssh-keygen -D`) or to Vault's SSH engine.
7. The housekeeping loop runs in every replica. Run it in one replica or as a CronJob until leader election lands.
8. Each HSM signature opens a new PKCS#11 session. Fine for hundreds of certificates a minute, not for bulk reissuance.
9. SCEP challenges are single use and expire (default 60 minutes), and a failed request still consumes its challenge. Single-DES request envelopes are refused unless `CERTADILLO_SCEP_ALLOW_DES=true`; run SCEP behind HTTPS either way.
10. `certadillo init` creates the root online. Production roots come from an offline key ceremony (see the runbook).

Open a private security advisory on the GitHub repository. Please do not file public issues for vulnerabilities.
